NeonFlux is designed as a Docker Compose stack with two app services. Convex is the durable runtime store and can be hosted separately or through the optional self-hosted Convex Compose file.

## Service roles

| Service | Owns                                                                    |
| ------- | ----------------------------------------------------------------------- |
| `bot`   | Fluxer gateway connection, bot lifecycle, deployment behavior bootstrap |
| `web`   | OAuth login, sessions, dashboard, public docs                           |

Both bot and web connect to Convex for durable runtime state. The bot owns deployment behavior bootstrap, including instance mode and public web URL, then writes it through the Convex-backed database boundary.

The web service keeps OAuth and session secrets in env, but reads deployment behavior from Convex. Bot, web-service, and user Convex JWTs use separate issuer/audience/key tuples: the bot receives only the bot private key, the web runtime receives the web-service and user private keys, and Convex receives all three public JWKS values.

## Local development

Local development can run app checks without app Postgres. Smoke tests and production-style runs need Convex runtime configuration.

<Callout title='Smoke tests need Convex' type='warn'>
    Bot lifecycle persistence, OAuth sessions, dashboard guild access, and token storage require complete Convex
    configuration.
</Callout>

## Deployment steps

<Steps>
    <Step>
        Configure bot environment for Fluxer token, custom status, instance mode, owner ids, and public web URL.
    </Step>
    <Step>Configure web environment for Fluxer OAuth, sessions, token encryption, and Convex access.</Step>
    <Step>Start the stack so the bot bootstraps deployment config.</Step>
    <Step>Open the web service and use `/dashboard` to reach manageable communities.</Step>
</Steps>
