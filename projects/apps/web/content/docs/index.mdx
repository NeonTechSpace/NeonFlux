## Current bot behavior

The bot currently owns:

- installation reconciliation in single- and multi-instance modes;
- prefix, help, ping, and contextless-mention responses;
- replay-safe message activity and member-join tracking with invite attribution;
- explicitly at-least-once member-leave tracking because Fluxer supplies no reliable leave event identity;
- a bounded, best-effort growth telemetry queue;
- durable dashboard posting delivery;
- server-structure observation, backups, drift checks, and reviewed Blueprint execution.

## Dashboard routes

Open `/dashboard` to choose an installed community you can manage. A selected community is managed at `/dashboard/{guildId}`.

| Surface             | Implemented tools                        |
| ------------------- | ---------------------------------------- |
| Overview            | Growth and message-activity summaries    |
| Create & Deliver    | Message Builder                          |
| Insights & Activity | Audit Events                             |
| Server Blueprint    | Overview, Backups, Compare, Deploy, Runs |
| Settings            | Command Prefix                           |

Features not listed here are not shipped dashboard routes.

## Loading behavior

The selected-community shell and feature identity remain visible during navigation. Each feature route loads its code and data independently, and only the unresolved data island shows cold-loading feedback. Confirmed content remains visible during background refresh, while errors and retries stay local to the affected feature.

## Security boundaries

Fluxer OAuth is the web login flow. Server code re-checks current manageable-community access before protected work. The browser receives a short-lived Convex user token scoped to communities the server confirmed.

The Fluxer bot token belongs only to the bot runtime. Dashboard live provider reads cross an authenticated internal bot-read service; web never receives or uses the bot token.

## Telemetry accuracy

Message activity stores a durable receipt keyed by community and message id before incrementing an aggregate. Member joins deduplicate by membership identity. Member leaves can overcount if Fluxer redelivers the same callback because no stable leave event id is available.

Telemetry processing is intentionally best effort so analytics cannot block commands or gateway routing. Overload and persistence failures are logged.
